# Ограничения и честные границы MVP

Этот документ отделяет реализованный продуктовый сценарий от демонстрационных данных и production-функций, которых в хакатонном контуре нет

## Режимы и происхождение данных

- Full является основным демонстрационным режимом. Он запускает реальный ML-сервис команды на подготовленных Parquet за 2019-2026 годы
- Lite предназначен для разработки и интеграционных проверок. В нём используется явно обозначенный `StubPredictor`, который не является обученной моделью
- Full не переключается на Stub при сбое. Скрипт запуска останавливается, если не хватает данных, ML не готов или API не вернул прогноз реальной модели
- Full и Lite используют разные Docker project names, базы и TLS volumes. Прогнозы двух режимов не смешиваются
- В API-режиме frontend показывает только данные backend. Автономный `mock` остаётся отдельным режимом прототипа и не подмешивается в API-ответы

## Данные объектов и телеметрии

- Backend загружает в PostgreSQL операционное окно журнала СМВУ, а не все 313 млн исторических строк. Полный архив используется ML-сервисом в Full-режиме
- Реальные координаты и планы объектов отсутствуют в выданных данных. Координаты детерминированные, но демонстрационные, а план объекта схематичный
- История ОДС, часть реестра оборудования, ремонтный backlog и финансовые показатели синтетические или производные. Интерфейс помечает такие значения как демонстрационные или расчётные
- Сентинел-значения и аномальные коды источника не маскируются под обычные измерения
- Внешние системы заказчика не подключены. СМВУ, ОДС, реестр оборудования и система заявок эмулируются локально, запись во внешние системы не выполняется

## ML

- Обученные модели, калибровки и код входят в `ml/`, но подготовленный журнал не хранится в Git из-за размера
- Full строит прогнозы по датчикам и объектам через внутренний HTTP-контракт ML-сервиса. Backend не вычисляет признаки модели самостоятельно
- Full использует явный исторический model clock: `as_of` и окно прогноза относятся к фактическому срезу архива, а `created_at` и SLA заявки относятся к текущему операционному времени. Frontend помечает такой результат как исторический ML-демо и не выдаёт его за прогноз на текущую дату
- При обновлении старого Full volume прогнозы реальных моделей без проверяемого `demo_clock` помечаются `is_invalidated=true`, исключаются из активной очереди и не блокируют повторный расчёт. Они остаются доступны по прямому id для аудита и связей с ранее созданными заявками
- Не каждый канал можно оценить на выбранном срезе: ML возвращает `insufficient_data` для групп без достаточной свежей истории. Текущий MVP не публикует агрегированную долю оценённых и пропущенных каналов отдельной метрикой, поэтому отсутствие риска нельзя трактовать как доказанное отсутствие риска для всех каналов
- Текущий MVP не реализует online learning, автоматическое переобучение, мониторинг дрейфа и production-регламент публикации новой версии модели
- `top_factors` и рекомендации отражают контракт текущей ML-реализации. Они не являются нормативным заключением инженера и требуют проверки человеком

## Заявки и роли

- Реализованы пять ролей: руководитель, старший диспетчер, диспетчер объекта, координатор ремонтов и инженер
- Инженерный grant привязан к назначенной заявке, но временно открывает полный технический контекст связанного объекта. Это продуктовый сценарий, а не доступ только к одной строке заявки
- Жизненный цикл заявки ручной. Статус меняется только разрешённым действием пользователя, а не автоматически по прошедшему времени
- Все действия жизненного цикла заявки используют idempotency key, исходное время команды и optimistic locking через `version`. Создание заявки поддерживает idempotency key и время клиента как необязательную парную опцию. Решения по риску используют `expected_version`, а чтение уведомления и выход из сессии не относятся к этому командному контракту
- Номер `ЗН-{год}-{порядковый}` защищён PostgreSQL transaction advisory lock. Это исключает коллизии между параллельными процессами в одной базе
- Руководитель имеет полный обзор, право управления, отмены и override. Интерфейс не маскирует руководителя под выездного инженера: полевой отчёт и его авторство остаются ответственностью назначенного исполнителя
- Закрытие ремонтной заявки не закрывает прогноз автоматически: выполненная работа и решение по прогнозу имеют разных ответственных и разные аудиторские события. Интерфейс показывает связанные заявки, после ремонта диспетчер отдельно оценивает актуальную телеметрию и принимает решение по прогнозу
- В MVP нет квалифицированной электронной подписи, фото до и после ремонта, складского контура и интеграции с закупками. Запчасти и трудозатраты фиксируются в отчёте как структурированные данные

## Офлайн-работа инженера

- PWA сохраняет офлайн-пакет только после явного действия инженера и только для заявки с действующим временным доступом
- Офлайн-пакет, черновик и очередь отправки хранятся в IndexedDB. Данные не шифруются отдельным прикладным ключом, поэтому production-версия потребует шифрования устройства, MDM и утверждённой модели доверенного устройства
- После локального истечения доступа пакет удаляется сразу. Серверный отзыв обнаруживается только при следующем online-обновлении, после чего пакет удаляется; полностью офлайн-устройство нельзя стереть удалённо. Максимальное локальное окно технического пакета составляет 12 часов. Несинхронизированный отчёт сохраняет безопасный статус ошибки, чтобы данные не исчезли незаметно
- Выход предупреждает о несинхронизированных отчётах и очищает локальные пакеты после подтверждения
- Кэшированная личность инженера действует не более семи дней и используется без token только при фактическом офлайн-запуске
- Полный PWA-сценарий требует HTTPS. Локальный gateway предоставляет самоподписанный сертификат

## Безопасность и эксплуатация

- LDAP/AD не подключён, потому что тестовый каталог заказчика недоступен. Локальные демо-пользователи проверяют RBAC и scope, но не заменяют корпоративную IAM-интеграцию
- Демо-логины можно показать на экране входа только build-флагом `VITE_SHOW_DEMO_CREDENTIALS=true`. Вне контролируемого стенда флаг нужно отключить
- TLS-сертификат локального стенда самоподписанный. Для эксплуатации требуется сертификат доверенного УЦ
- Офлайн-пакеты содержат синтетический технический контекст. Для реальных схем дополнительно нужны классификация данных, политика хранения и удалённое стирание
- Реализованы только технические меры защиты MVP. Полное юридическое и организационное соответствие 149-ФЗ и 152-ФЗ не заявляется
- Push-уведомления ОС, SMS и почта не реализованы. Есть уведомления внутри приложения

## Нагрузка и отказоустойчивость

- Регрессионный тест проверяет 20 конкурентных транзакций генерации номера заявки и параллельный API create с idempotent replay. Startup smoke дополнительно проверяет 20 независимых авторизованных сессий пяти ролей с одновременными защищёнными запросами
- Это не заменяет длительное нагрузочное, soak- и failover-тестирование всей системы. Перед production нужны профиль нагрузки, SLO, резервное копирование, мониторинг и проверка восстановления
- Compose рассчитан на один локальный узел. Масштабирование PostgreSQL, gateway, backend и ML по нескольким узлам в MVP не настраивается
