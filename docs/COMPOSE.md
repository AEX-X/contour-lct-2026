# Запуск через Docker Compose

Инструкция для всех, кто поднимает решение у себя: команда, ML-команда, проверяющие. Нужны только Docker и Docker Compose v2 (Docker Desktop на Windows/macOS или Docker Engine на Linux) и свободные порты 8443 и 8080.

Есть два режима:

| Режим | Команда | Что нужно положить заранее | Прогнозы |
|---|---|---|---|
| Lite | `.\scripts\start-lite.ps1` | ничего | явно обозначенный `StubPredictor` |
| Full | `.\scripts\start-full.ps1` | подготовленный журнал ML в `ml-data/` | обученные модели ML-команды |

Используй скрипты, а не сырой `docker compose up`: они задают разные project names и volumes для Full и Lite, проверяют конфигурацию, ждут healthchecks и выполняют smoke-test

## Режим без ML

```
.\scripts\start-lite.ps1
```

Поднимаются три контейнера. Frontend собирается первым stage образа `proxy` и доступен через тот же origin, что и API:

| Контейнер | Что это | Снаружи |
|---|---|---|
| `db` | PostgreSQL 16 | не публикуется |
| `app` | backend (FastAPI) | не публикуется |
| `proxy` | nginx с TLS 1.2/1.3 | `https://localhost:8443`, `http://localhost:8080` → перенаправление на HTTPS |

Всё, что нужно backend, уже лежит в репозитории: датасет организаторов в `data/` (справочник объектов, справочник каналов, операционное окно журнала событий), миграции, демо-пользователи. Сертификат создаётся сам при первом запуске.

Проверка: `curl -k https://localhost:8443/health` → `{"status":"ok"}`. Документация API — `https://localhost:8443/docs`, демо-вход — `manager` / `manager123`.

## Режим с ML-сервисом

К трём контейнерам добавляется четвёртый — `ml`, прогнозный сервис ML-команды (код в `ml/`). Backend обращается к нему внутри сети compose по адресу `http://ml:8090`; наружу ML не публикуется.

### Что положить перед запуском

Модели, калибровки и код ML лежат в репозитории (`ml/outputs/...`), справочник каналов берётся из `data/`. **В git нет только подготовленного журнала** — он слишком большой (исходный архив 2019–2026 годов — около 1,75 ГБ в `.7z`). Его нужно положить в папку `ml-data/` в корне репозитория:

```
<папка репозитория>/
  docker-compose.yml
  docker-compose.ml.yml
  ml-data/            <- создать; в git не попадает
    2019.parquet
    2020.parquet
    ...
    2026.parquet
```

- Нужны именно файлы `20??.parquet` из каталога `work/ml-prepared` ML-репозитория (годовые наблюдения). Другие файлы оттуда (`episodes-900.parquet`, `training-examples-*.parquet`) сервису не нужны, лишние файлы он игнорирует.
- Кладите **все годы 2019–2026**. Окно признаков — 30 суток, но признаки «сколько канал наблюдается» и «было ли у канала такое состояние раньше» считаются по всей истории. С одним 2026 годом сервис запустится, но прогнозы будут отличаться от проверенных ML-командой.
- Где взять файлы: у ML-команды (готовый каталог `work/ml-prepared`) или собрать самим из архива организаторов по `ml/docs/REPRODUCE.md`. Контрольные суммы исходного архива — `ml/docs/sources.json`.
- Если данные лежат в другом месте, не копируйте их, а укажите путь: `ML_DATA_DIR=D:/ml-prepared`.

### Запуск

```
.\scripts\start-full.ps1
```

PowerShell, если данные не в `ml-data/`:

```
.\scripts\start-full.ps1 -MlDataDir "D:\ml-prepared"
```

Порядок старта соблюдается сам: `app` ждёт, пока `ml` загрузит журнал и начнёт отвечать на `/health`. Это важно: backend запрашивает прогнозы один раз при старте. На полном журнале загрузка ML и первичный расчёт рисков занимают от десятков секунд до нескольких минут; в Full overlay для этого задан отдельный 15-минутный healthcheck start period. Первая сборка образа ML с установкой зависимостей тоже может занять несколько минут

Проверка: `GET https://localhost:8443/api/v1/risks` под `manager`. Прогнозы моделей видны по полю `model`: `hgb-v2-run002-…` — по датчикам, `hgb-object-run008-…` и `hgb-object-run009-…` — по объектам (`target.type = "facility"`); у объектных рисков заполнены `verdict` и `blind_spots`. `GET /api/v1/model-quality` отдаёт метрики с заголовком `X-Data-Source: ml_service`.

Вкладка «Качество модели» работает и без ML-сервиса: в Lite режиме `/model-quality` отдаёт тот же файл метрик из `ml/` (`X-Data-Source: file`).

### Временный командный preview

Для короткой внешней проверки уже запущенного Full-контура:

```powershell
.\scripts\start-preview.ps1
```

Контейнер `preview-gateway` переводит входящий HTTP-трафик туннеля во внутренний HTTPS к основному nginx, а контейнер `preview` устанавливает исходящее SSH-соединение с localhost.run и получает случайный адрес `*.lhr.life`. Оба контейнера находятся только в сети `edge`. PostgreSQL, backend и ML внешних портов не получают. Базовые образы закреплены по digest, процессы работают без Linux capabilities, с read-only filesystem и `no-new-privileges`

Анонимный туннель меняет URL после пересоздания и подходит только для временного командного тестирования. Он работает, пока включены этот компьютер, Docker и оба preview-контейнера. Остановить его можно командой:

При повторном запуске `start-preview.ps1` выполняется сквозная проверка опубликованного `/health`. Если SSH-процесс ещё работает, но внешний маршрут уже отвечает ошибкой, скрипт пересоздаёт только `preview`, получает новый адрес и не трогает основной стек или данные

```powershell
.\scripts\stop-preview.ps1
```

### Переменные режима с ML

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `ML_DATA_DIR` | папка с `20??.parquet` на хосте | `./ml-data` |
| `ML_DEMO_ANCHOR` | «текущее время» для ML: журнал заканчивается 30.06.2026, а backend спрашивает прогноз на сейчас; сервис сдвигает время к этой точке | `2026-06-20T00:00:00` |

## Общие переменные

Задаются перед командой запуска или в файле `.env` рядом с `docker-compose.yml`. Скрипты запуска читают тот же файл и передают его Compose явно. Приоритет: параметр скрипта, переменная текущего процесса, `.env`, значение по умолчанию. Полный список — в `README.md`, раздел «Конфигурация».

| Переменная | Зачем менять |
|---|---|
| `HTTPS_PORT`, `HTTP_PORT` | порты 8443/8080 заняты |
| `CORS_ALLOWED_ORIGINS` | адрес браузерного фронтенда, если он не на `localhost:3000`/`5173` |
| `VITE_SHOW_DEMO_CREDENTIALS` | `true` только для контролируемого хакатонного стенда; вне демо скрывает быстрый выбор аккаунтов |

Lite всегда принудительно оставляет `ML_PREDICTOR_URL` пустым, даже если такая переменная случайно задана в оболочке. Full всегда использует внутренний адрес `http://ml:8090`. Внешний ML не является поддерживаемым режимом этих двух профилей

## Backend-тесты

Тесты нельзя запускать против рабочей базы: часть сценариев создаёт и изменяет записи. Сначала запусти Lite или Full, затем из корня репозитория выполни:

```powershell
.\scripts\test-backend.ps1 -Mode Lite
# или, если запущен Full
.\scripts\test-backend.ps1 -Mode Full
```

Скрипт создаёт базу со случайным именем, применяет в ней все миграции, запускает `pytest -q` внутри контейнера `app` и удаляет только созданную им базу даже при падении тестов. Рабочая БД выбранного режима не изменяется

## Остановка и сброс

```
.\scripts\stop.ps1 -Mode Full
.\scripts\stop.ps1 -Mode Lite
.\scripts\reset.ps1 -Mode Full -Force
.\scripts\reset.ps1 -Mode Lite -Force
```

`stop` сохраняет базу и сертификат. `reset` удаляет volumes выбранного режима, но не изменяет файлы в `ml-data`

## Если что-то не так

| Симптом | Причина и что сделать |
|---|---|
| `ml` не становится healthy, в `docker compose logs ml` — `FileNotFoundError` | в `ml-data/` (или `ML_DATA_DIR`) нет файлов `20??.parquet` |
| рисков от моделей ML нет, в `docker compose logs app` — `insufficient_data ... stale_journal` | `ML_DEMO_ANCHOR` позже конца журнала; верните значение по умолчанию |
| в логе `app` — `N sensor group(s) skipped ... unknown_channel` | у части каналов нет записей в журнале ML; для таких каналов прогноза нет — это нормально |
| `ml` не становится healthy, в `docker compose logs ml` — несовпадение SHA-256 модели | файлы моделей в `ml/` повреждены или изменены; обновите `ml/` из репозитория ML-команды (см. `README.md`) |
| браузер предупреждает о сертификате | сертификат самоподписанный; примите его один раз или замените своим (том `proxy_certs`) |
| порт уже занят | задайте `HTTPS_PORT` / `HTTP_PORT` |
| браузерный фронтенд получает ошибку CORS | добавьте его адрес в `CORS_ALLOWED_ORIGINS` |
